# 杏林学堂——医友圈即时通讯技术方案

## 1. 文档说明

本文档用于设计“杏林学堂——中医学习系统”的医友圈即时通讯模块，覆盖好友关系、单聊、群聊、消息收发、WebSocket 长连接、在线状态、消息序号、未读数、离线消息、消息持久化、安全校验、限流、日志审计、前端页面和部署方案。

医友圈的核心目标是让学习者围绕课程、中医知识和学习进度进行实时交流。该模块不承担论坛长内容沉淀，也不承担 AI 问答；它侧重低延迟、可达性、消息顺序和在线互动。

## 2. 模块定位

### 2.1 服务名称

后端服务：`chat-service`

前端模块：`FriendCircleView`、`ChatRoomView`

### 2.2 核心职责

1. WebSocket 连接管理。
2. 用户在线状态维护。
3. 单聊消息。
4. 群聊消息。
5. 会话列表。
6. 未读消息数。
7. 消息历史分页。
8. 消息撤回。
9. 图片、视频、文件消息元数据。
10. 好友关系。
11. 群成员管理。
12. 消息可靠投递。
13. 聊天审计与安全风控。

### 2.3 不属于本模块的职责

- 用户注册登录：用户服务负责。
- 视频文件上传与播放：视频服务负责。
- AI 问答：AI 服务负责。
- 论坛帖子和评论：论坛服务负责。
- 内容推荐流：后续社区推荐服务负责。

## 5. 通信协议设计

## 5.1 WebSocket 地址

```text
ws://域名/ws/chat?token={accessToken}
```

正式环境建议：

```text
wss://域名/ws/chat?token={accessToken}
```

Token 也可以通过 `Sec-WebSocket-Protocol` 或连接建立后的认证消息传递。第一阶段用 query token 实现简单，但日志中必须过滤 token。

## 5.2 连接鉴权流程

```text
客户端发起 WebSocket 连接
  |
服务端解析 Token
  |
校验 JWT 签名和过期时间
  |
校验用户状态
  |
绑定 userId 与 sessionId
  |
写入 Redis 在线状态
  |
返回 CONNECTED 事件
```

连接失败：

- Token 缺失：关闭连接，错误码 401。
- Token 过期：关闭连接，提示重新登录。
- 用户禁用：关闭连接，错误码 403。
- 连接数超限：关闭连接，错误码 429。

## 5.3 客户端上行消息格式

```json
{
  "clientMsgId": "uuid",
  "type": "CHAT_MESSAGE",
  "conversationId": 10001,
  "payload": {
    "contentType": "TEXT",
    "content": "这个课程讲得不错",
    "mentions": []
  },
  "timestamp": 1710000000000
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| clientMsgId | 客户端生成的幂等 ID |
| type | 消息类型 |
| conversationId | 会话 ID |
| payload | 业务内容 |
| timestamp | 客户端时间，仅供展示参考 |

## 5.4 服务端下行消息格式

```json
{
  "type": "CHAT_MESSAGE",
  "serverMsgId": 90001,
  "clientMsgId": "uuid",
  "conversationId": 10001,
  "seq": 128,
  "fromUserId": 10001,
  "payload": {
    "contentType": "TEXT",
    "content": "这个课程讲得不错"
  },
  "sentAt": "2025-03-21T10:20:30"
}
```

## 5.5 消息类型

| 类型 | 方向 | 说明 |
| --- | --- | --- |
| CONNECTED | 服务端 -> 客户端 | 连接成功 |
| PING | 客户端 -> 服务端 | 心跳 |
| PONG | 服务端 -> 客户端 | 心跳响应 |
| CHAT_MESSAGE | 双向 | 聊天消息 |
| MESSAGE_ACK | 服务端 -> 客户端 | 服务端确认接收 |
| MESSAGE_READ | 客户端 -> 服务端 | 已读上报 |
| MESSAGE_RECALL | 双向 | 消息撤回 |
| TYPING | 双向 | 正在输入 |
| ERROR | 服务端 -> 客户端 | 错误 |

## 6. 核心功能

## 6.1 单聊

单聊会话由两个用户组成。

创建规则：

- 用户 A 给用户 B 发送第一条消息时自动创建会话。
- 如果会话已存在，复用原会话。
- 被拉黑用户不能创建会话。
- 禁用用户不能发送消息。

会话唯一索引：

```text
uk_private_pair(min_user_id, max_user_id)
```

## 6.2 群聊

第一阶段支持学习小组群聊：

- 创建群。
- 修改群名称。
- 加入群。
- 退出群。
- 群主踢人。
- 群成员列表。
- 群聊消息。

群权限：

| 操作 | 权限 |
| --- | --- |
| 发消息 | 群成员 |
| 修改群名 | 群主、管理员 |
| 踢人 | 群主、管理员 |
| 解散群 | 群主 |
| 禁言 | 管理员，第二阶段 |

## 6.3 消息内容类型

第一阶段：

- TEXT 文本
- IMAGE 图片
- VIDEO 视频
- FILE 文件
- COURSE_CARD 课程卡片

第二阶段：

- AUDIO 语音
- AI_SUMMARY AI 总结
- FORUM_POST_CARD 帖子卡片

媒体文件本身存 OSS，聊天消息只保存元数据：

```json
{
  "contentType": "IMAGE",
  "url": "https://bucket.oss-cn-beijing.aliyuncs.com/chat/images/a.png",
  "objectKey": "chat/images/2025/03/21/a.png",
  "width": 1280,
  "height": 720,
  "size": 340120
}
```

## 6.4 消息序号设计

每个会话维护单调递增 `seq`。

Redis Key：

```text
chat:conversation:seq:{conversationId}
```

发送消息时：

```text
INCR chat:conversation:seq:{conversationId}
```

Redis `INCR` 是原子操作，因此同一会话下并发发送也能保证 seq 不重复。客户端按 `seq` 排序，避免消息乱序。

## 6.5 消息实时存储

近期消息写 Redis ZSet：

```text
chat:message:zset:{conversationId}
score = seq
value = messageJson
```

用途：

- 快速拉取最近消息。
- 客户端断线重连后按 seq 补消息。
- 削峰，降低 MySQL 压力。

TTL：

```text
7 天
```

MySQL 用于长期持久化。

## 6.6 消息落库策略

第一阶段建议同步落库，逻辑简单：

```text
收到消息
  |
校验权限
  |
Redis INCR 生成 seq
  |
写 MySQL message
  |
写 Redis ZSet
  |
投递给在线用户
  |
更新未读
```

第二阶段高并发可改为异步落库：

```text
收到消息
  |
Redis INCR 生成 seq
  |
写 Redis ZSet
  |
发送 RabbitMQ persist event
  |
立即 ACK 客户端
  |
消费者批量写 MySQL
```

异步落库必须增加：

- outbox 或 Redis 待落库队列。
- 消费失败重试。
- 死信队列。
- 定时对账任务。

## 6.7 未读数

Redis Hash：

```text
chat:unread:{userId}
field = conversationId
value = unreadCount
```

收到消息时：

- 发送者不加未读。
- 在线且正在打开该会话的成员可不加未读。
- 其他成员未读 +1。

已读上报：

```text
chat:read:seq:{conversationId}:{userId} -> lastReadSeq
```

用户打开会话：

1. 上报最后读取 seq。
2. Redis 未读清零。
3. MySQL 更新会话成员 last_read_seq。

## 6.8 离线消息

用户断线后：

- 消息仍写 MySQL 和 Redis ZSet。
- 未读数增加。
- 用户下次登录拉取会话列表看到未读。
- 进入会话后按 `lastReadSeq` 拉取历史消息。

拉取补偿接口：

```http
GET /api/chat/conversations/{conversationId}/messages?afterSeq=100&limit=50
```

## 6.9 消息 ACK

客户端发送消息后状态：

```text
SENDING -> SENT -> DELIVERED -> READ
```

第一阶段：

- `SENT`：服务端已接收并分配 seq。
- `READ`：对方已读。

第二阶段：

- `DELIVERED`：已推送到对方在线设备。

客户端使用 `clientMsgId` 进行幂等：

```text
chat:client-msg:{userId}:{clientMsgId}
TTL: 24 小时
```

如果用户重复发送同一个 clientMsgId，服务端直接返回原 ACK，不重复写消息。

## 6.10 消息撤回

规则：

- 只能撤回自己发送的消息。
- 发送后 2 分钟内可撤回。
- 管理员可撤回违规消息。
- 撤回后内容不再展示，但保留审计记录。

流程：

```text
用户请求撤回
  |
校验登录
  |
查询消息
  |
校验发送人和时间窗口
  |
更新消息 status = RECALLED
  |
删除或更新 Redis ZSet 中消息快照
  |
广播 MESSAGE_RECALL
```

## 6.11 在线状态

Redis Key：

```text
chat:online:user:{userId} -> sessionCount
TTL: 90 秒
```

每个 WebSocket 连接维护：

```text
chat:online:session:{sessionId} -> userId
TTL: 90 秒
```

心跳每 30 秒刷新 TTL。

同一用户允许多端在线：

- PC 浏览器。
- 手机浏览器。
- 后续 App。

## 7. 数据库设计

## 7.1 chat_conversation 会话表

```sql
CREATE TABLE chat_conversation (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_type VARCHAR(32) NOT NULL COMMENT 'PRIVATE GROUP',
  title VARCHAR(128) DEFAULT NULL,
  avatar VARCHAR(512) DEFAULT NULL,
  min_user_id BIGINT DEFAULT NULL,
  max_user_id BIGINT DEFAULT NULL,
  last_message_id BIGINT DEFAULT NULL,
  last_message_preview VARCHAR(255) DEFAULT NULL,
  last_message_time DATETIME DEFAULT NULL,
  status VARCHAR(32) NOT NULL DEFAULT 'ACTIVE',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_private_pair (min_user_id, max_user_id),
  KEY idx_last_time (last_message_time)

```

## 7.2 chat_conversation_member 会话成员表

```sql
CREATE TABLE chat_conversation_member (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  member_role VARCHAR(32) NOT NULL DEFAULT 'MEMBER',
  muted_until DATETIME DEFAULT NULL,
  last_read_seq BIGINT NOT NULL DEFAULT 0,
  joined_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  left_at DATETIME DEFAULT NULL,
  status VARCHAR(32) NOT NULL DEFAULT 'ACTIVE',
  UNIQUE KEY uk_conversation_user (conversation_id, user_id),
  KEY idx_user_status (user_id, status),
  KEY idx_conversation_status (conversation_id, status)
) COMMENT='会话成员表';
```

## 7.3 chat_message 消息表

```sql
CREATE TABLE chat_message (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  conversation_id BIGINT NOT NULL,
  seq BIGINT NOT NULL,
  sender_id BIGINT NOT NULL,
  client_msg_id VARCHAR(64) NOT NULL,
  content_type VARCHAR(32) NOT NULL,
  content TEXT DEFAULT NULL,
  media_url VARCHAR(512) DEFAULT NULL,
  media_object_key VARCHAR(512) DEFAULT NULL,

  sent_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  recalled_at DATETIME DEFAULT NULL,
  UNIQUE KEY uk_conversation_seq (conversation_id, seq),
  UNIQUE KEY uk_sender_client_msg (sender_id, client_msg_id),
  KEY idx_conversation_time (conversation_id, sent_at),
  KEY idx_sender_time (sender_id, sent_at)
) COMMENT='聊天消息表';
```

## 11. 前端设计

移动端：

功能：

- 消息气泡。

- 发送状态。

- 图片预览。
- 课程卡片。
- 自动滚动到底部。
- 上拉加载历史消息。

## 11.4 输入区

支持：

- 文本输入。
- 表情快捷插入。
- 图片上传。
- 文件上传。
- 发送课程卡片。
- Enter 发送，Shift + Enter 换行。

前端必须做：

- 空消息禁止发送。
- 文本长度限制。
- 文件大小限制。
- 文件类型校验。
- 发送中状态展示。

## 11.5 断线重连

前端 WebSocket 断开后：

1. 立即展示“连接中断”。
2. 1 秒后第一次重连。
3. 失败后指数退避，最多 30 秒间隔。
4. 重连成功后调用补消息接口。
5. 使用最后已收到 seq 补齐消息。

## 12. 高并发设计

## 12.1 连接数控制

限制：

| 维度 | 阈值 |
| --- | ---: |
| 单用户连接数 | 5 |
| 单 IP 连接数 | 50 |
| 单实例连接数 | 根据机器配置压测确定 |

超过后拒绝连接。

## 12.2 发送限流

| 维度 | 阈值 |
| --- | ---: |
| 单用户文本消息 | 60 条/分钟 |
| 单会话消息 | 300 条/分钟 |
| 图片消息 | 20 条/分钟 |
| 好友申请 | 10 次/小时 |

命中限流返回：

```json
{
  "type": "ERROR",
  "code": 429,
  "message": "发送过于频繁，请稍后再试"
}
```

## 12.3 热点群聊

热点群聊容易导致广播压力。

优化：

- 群成员分页加载。
- 在线成员 Redis 缓存。
- 只向在线成员推送。
- 离线成员只更新未读，不逐条通知。
- 大群消息可按分片异步广播。
- 群消息读扩散，未读按成员 Hash 维护。

## 12.4 消息顺序

顺序保证范围：

- 同一会话内按 seq 有序。
- 不保证不同会话之间全局有序。

服务端分配 seq 后再投递，客户端以 seq 排序。

## 12.5 消息可靠性

保证：

- 客户端 clientMsgId 幂等。
- 服务端分配 serverMsgId。
- MySQL 唯一索引防重复。
- Redis ZSet 支持短期补偿。
- RabbitMQ 异步时使用手动 ACK。

不保证：

- 第一阶段不做端到端加密。
- 第一阶段不保证消息必达通知到离线设备，只保证用户登录后可拉取。

## 13. 高可用设计

## 13.1 多实例 WebSocket

多实例部署时，用户可能连接到任意实例。需要：

- Redis 记录 userId -> instanceId/sessionId。
- RabbitMQ 或 Redis Pub/Sub 做跨实例消息分发。
- Nginx 支持 WebSocket 升级。

第一阶段单 ECS 单实例可以先本地内存维护 session，保留 Redis 在线状态接口，后续平滑扩展。

## 13.2 依赖降级

| 依赖 | 异常处理 |
| --- | --- |
| MySQL 异常 | 禁止发送新消息，避免消息不可持久化 |
| Redis 异常 | 消息仍可写 MySQL，但在线状态和未读可能降级 |
| RabbitMQ 异常 | 同步路径不受影响，异步通知暂停 |
| OSS 异常 | 图片/文件消息上传失败，文本消息可用 |

## 13.3 心跳机制

客户端每 30 秒发送 PING。

服务端：

- 收到 PING 返回 PONG。
- 90 秒未收到心跳则关闭连接。
- 清理 Redis session。
- 更新在线状态。

## 13.4 优雅停机

服务停机时：

1. 停止接收新 WebSocket 连接。
2. 通知客户端 `SERVER_SHUTDOWN`。
3. 等待短时间让客户端重连。
4. 关闭连接。
5. 清理在线状态。

## 14. 安全设计

## 14.1 鉴权与越权

所有消息发送必须校验：

- 用户已登录。
- 用户属于该会话。
- 用户未被禁言。
- 用户账号未被禁用。
- 群组状态正常。

客户端传入的 `fromUserId` 一律忽略，发送人必须取自 Token。

## 14.2 内容安全

消息内容需要：

- 长度限制。
- HTML 转义。
- 敏感词过滤。
- 链接风险提示。
- 图片文件类型检测。
- 文件后缀和 MIME 双重校验。

## 14.3 防骚扰

措施：

- 好友申请限流。
- 陌生人消息限制。
- 拉黑用户。
- 举报消息。
- 管理员撤回违规消息。

## 14.4 隐私保护

禁止：

- 普通用户查询其他用户聊天记录。
- 群成员外读取群消息。
- 日志打印完整聊天内容。
- URL 中 token 被访问日志记录，Nginx 日志需脱敏或避免记录 query。

## 15. 日志与可观测性

## 15.1 请求日志

HTTP 接口记录：

- traceId
- userId
- method
- path
- status
- costMs
- ip

WebSocket 记录：

```text
INFO ws connected userId={} sessionId={} ip={}
INFO ws disconnected userId={} sessionId={} reason={}
WARN ws auth failed ip={} reason={}
WARN chat send rate limited userId={} conversationId={}
ERROR chat message send failed userId={} conversationId={} clientMsgId={} traceId={} error={}
```

## 15.2 消息日志

不打印完整内容，只打印摘要：

```text
INFO chat message accepted userId={} conversationId={} seq={} contentType={} size={}
INFO chat message delivered conversationId={} seq={} onlineReceiverCount={}
INFO chat read reported userId={} conversationId={} lastReadSeq={}
WARN chat message duplicate userId={} clientMsgId={}
WARN chat recall denied userId={} messageId={} reason={}
```

## 15.3 指标

需要统计：

- WebSocket 当前连接数。
- 每分钟消息数。
- 消息发送成功率。
- 消息平均延迟。
- 未读更新失败次数。
- 重复消息数。
- 限流次数。
- 在线用户数。
- 群聊广播耗时。

## 17. 测试方案

### 17.1 功能测试

- 登录后 WebSocket 连接成功。
- 未登录连接失败。
- 单聊发送文本消息成功。
- 群聊发送消息成功。
- 会话列表展示最后一条消息。
- 未读数正确增加和清零。
- 历史消息分页正确。
- 重复 clientMsgId 不重复写入。
- 消息撤回成功。
- 非本人撤回失败。
- 好友申请和处理成功。

### 17.2 并发测试

- 同一会话 100 并发发送，seq 不重复不乱序。
- 1000 个连接保持心跳稳定。
- 群聊 100 人在线广播稳定。
- 同一 clientMsgId 并发提交只生成一条消息。

### 17.3 安全测试

- 用户不能向未加入的会话发消息。
- 普通成员不能踢人。
- 被拉黑用户不能发起单聊。
- XSS 文本不会执行。
- URL query 中 token 不进入业务日志。

### 17.4 可靠性测试

- WebSocket 断线后自动重连。
- 重连后按 lastSeq 补消息。
- Redis 重启后不影响历史消息读取。
- MySQL 异常时发送失败且不假装成功。
- 服务重启后在线状态能自动过期清理。

## 18. 开发优先级

第一阶段 MVP：

1. WebSocket 鉴权连接。
2. 单聊会话。
3. 文本消息发送。
4. Redis INCR 生成 seq。
5. MySQL 消息持久化。
6. Redis ZSet 近期消息。
7. 会话列表和历史消息。
8. 未读数。
9. 断线重连和补消息。
10. 日志和限流。

第二阶段增强：

1. 群聊。
2. 图片、文件消息。
3. 好友关系。
4. 消息撤回。
5. 跨实例消息分发。
6. 异步批量落库。
7. 举报和风控。

## 19. 总结

医友圈即时通讯的核心是“顺序、实时、可恢复”。设计上用 WebSocket 承接实时收发，用 Redis 维护在线状态、未读数和会话 seq，用 MySQL 保存长期消息，用 RabbitMQ 承接异步审计和扩展任务。

关键原则：

- 服务端生成 seq，保证同会话有序。
- clientMsgId 幂等，避免重复发送。
- 用户身份只信 Token，不信客户端 userId。
- 消息内容日志脱敏。
- 离线消息通过历史接口补齐。
- 第一阶段同步落库更稳，第二阶段再引入异步批量落库提升吞吐。
