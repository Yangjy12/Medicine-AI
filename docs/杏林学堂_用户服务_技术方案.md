# 杏林学堂——用户服务技术方案

## 1. 文档说明

### 1.1 文档目的

本文档用于设计“杏林学堂——中医学习系统”的用户服务，覆盖用户注册登录、身份认证、用户资料、每日签到、积分体系、成长等级、安全校验、高并发处理、高可用部署、日志审计和监控告警等技术细节。

用户服务是平台的基础服务，视频学习中心、AI 助手、杏林论坛、医友圈、积分任务、后台管理等模块都依赖用户服务提供身份、权限、用户状态和成长数据。

### 1.2 当前问题说明

当前视频学习中心第一版已经完成可运行闭环，但日志设计不完整，主要缺少：

- 请求入口日志
- 业务关键节点日志
- 异常堆栈日志
- 用户行为审计日志
- MQ 事件发送与消费日志
- Redis/MySQL/ES 降级日志
- traceId 跨服务链路日志

后续所有新服务，包括用户服务，应从第一版就内置日志、审计、链路追踪和指标埋点。视频学习中心也需要按本文第 15 节的日志规范进行补齐。

## 2. 用户服务定位

### 2.1 服务名称

用户服务：`user-service`

### 2.2 服务职责

用户服务负责平台用户身份与成长体系，主要包括：

1. 用户注册
2. 用户登录
3. Token 签发与刷新
4. 用户登出
5. 用户资料维护
6. 用户账号状态管理
7. 每日签到
8. 连续签到统计
9. 积分账户
10. 积分流水
11. 积分任务幂等
12. 用户等级
13. 权限角色
14. 安全风控
15. 登录日志
16. 操作审计日志

### 2.3 不属于用户服务的职责

以下能力不直接放入用户服务：

- 视频播放、搜索、学习记录：视频服务负责。
- AI 问答、知识库检索：AI 助手服务负责。
- 发帖、评论、点赞：论坛服务负责。
- 即时聊天：聊天服务负责。
- 课程内容管理：课程/视频服务负责。

用户服务可以接收其他模块的事件，例如“视频学习完成”“发帖成功”“评论成功”，然后根据积分规则发放积分。

## 5. 核心业务模块

## 5.1 注册模块

### 5.1.1 注册方式

第一阶段支持：

- 用户名 + 密码注册
- 手机号 + 密码注册，可后续接短信验证码

第二阶段扩展：

- 手机验证码登录
- 微信登录
- 邮箱注册

### 5.1.2 注册流程

```text
用户提交注册信息
  |
参数校验
  |
图形验证码/短信验证码校验
  |
用户名/手机号唯一性校验
  |
密码强度校验
  |
密码 BCrypt 哈希
  |
写入 user 表
  |
初始化 user_account 积分账户
  |
记录注册审计日志
  |
返回注册成功
```

### 5.1.3 参数校验

用户名：

- 长度 4 到 32。
- 只允许中文、英文、数字、下划线。
- 不允许包含手机号、身份证号等敏感格式。

手机号：

- 必须符合中国大陆手机号格式。
- 存储前建议规范化。
- 展示时脱敏。

密码：

- 长度 8 到 32。
- 至少包含字母和数字。
- 禁止纯数字、纯字母。
- 禁止与用户名、手机号后四位完全一致。
- 禁止常见弱密码，例如 `12345678`、`password`、`qwerty123`。

昵称：

- 长度 2 到 20。
- 过滤 HTML 标签。
- 过滤敏感词。
- 不允许冒充管理员。

### 5.1.4 并发唯一性

用户名和手机号唯一性不能只靠代码查询判断，必须依赖数据库唯一索引：

```text
uk_username(username)
uk_phone(phone)
```

并发注册时，如果两个请求同时通过前置查询，最终由唯一索引保证只有一个插入成功。后端捕获唯一键冲突并返回友好提示。

## 5.2 登录模块

### 5.2.1 登录方式

第一阶段：

- 用户名 + 密码
- 手机号 + 密码

第二阶段：

- 手机验证码登录
- 第三方 OAuth 登录

### 5.2.2 登录流程

```text
用户提交账号和密码
  |
IP/账号限流校验
  |
参数格式校验
  |
查询用户
  |
账号状态校验
  |
密码 BCrypt 校验
  |
登录失败计数清零
  |
生成 Access Token
  |
生成 Refresh Token
  |
Refresh Token 写入 Redis
  |
记录登录日志
  |
返回 Token 和用户信息
```

### 5.2.3 登录失败处理

为了防止撞库和暴力破解：

- 同一账号 5 分钟内密码错误 5 次，临时锁定 15 分钟。
- 同一 IP 1 分钟内登录失败超过 20 次，限流 10 分钟。
- 同一设备指纹异常高频切换账号，记录风险日志。

Redis key：

```text
user:login:fail:account:{account}
user:login:fail:ip:{ip}
user:login:lock:account:{account}
```

## 5.3 Token 鉴权模块

### 5.3.1 Token 设计

Access Token：

- 使用 JWT。
- 有效期建议 2 小时。
- 用于接口鉴权。
- 不存储敏感信息。

Refresh Token：

- 使用随机安全字符串。
- 有效期建议 7 天或 30 天。
- 存储在 Redis。
- 可主动撤销。
- 用于换取新的 Access Token。

### 5.3.2 JWT Claims

JWT 中建议包含：

```json
{
  "sub": "10001",
  "username": "student001",
  "roles": ["USER"],
  "tokenVersion": 3,
  "iat": 1710000000,
  "exp": 1710007200,
  "jti": "uuid"
}
```

禁止放入：

- 密码
- 手机号明文
- 身份证号
- 地址
- 积分明细
- 其他隐私数据

### 5.3.3 Refresh Token Redis 设计

```text
user:refresh:{userId}:{deviceId} -> refreshTokenHash
TTL: 7 天或 30 天
```

Refresh Token 不建议明文存 Redis，建议存 SHA-256 哈希。

### 5.3.4 Token 失效机制

支持以下失效方式：

1. 用户主动登出：删除 Redis 中当前设备 Refresh Token。
2. 修改密码：用户 tokenVersion + 1，使旧 Access Token 失效。
3. 管理员封禁：用户状态改为 DISABLED，网关鉴权时拒绝。
4. 踢下线：删除指定设备 Refresh Token。

### 5.3.5 网关鉴权

后续接入 API 网关时，统一在网关做：

- JWT 签名校验。
- 过期校验。
- 黑名单校验。
- 用户状态校验。
- 角色权限校验。
- 将用户 ID 写入 `X-User-Id` 请求头。

内部服务不信任客户端传入的 `X-User-Id`，只信任网关透传的可信请求头，并通过内网或签名头防止伪造。

## 5.5 签到模块

### 5.5.1 功能说明

用户每日签到获得积分。系统支持：

- 今日签到
- 查询当月签到日历
- 查询连续签到天数
- 查询累计签到天数
- 签到触发积分奖励

### 5.5.2 Redis Bitmap 设计

按用户和月份拆分 Bitmap：

```text
user:checkin:{userId}:{yyyyMM}
```

offset：

```text
dayOfMonth - 1
```

例如 2025-03-21 签到：

```text
SETBIT user:checkin:10001:202503 20 1
```

### 5.5.3 签到流程

```text
用户点击签到
  |
登录校验
  |
获取当天日期
  |
Redis SETBIT 设置当天签到位
  |
根据 SETBIT 旧值判断是否重复签到
  |
首次签到则写 MySQL 签到流水
  |
发送签到积分事件到 RabbitMQ
  |
返回签到结果、连续天数和奖励积分
```

### 5.5.4 并发签到控制

Redis `SETBIT` 是原子操作。多个请求同时签到时：

- 第一个请求将 0 设置为 1。
- 后续请求发现旧值已是 1。
- 后续请求直接返回“今日已签到”，不重复发积分。

为了进一步保证积分不重复，积分流水使用幂等键：

```text
CHECKIN:{userId}:{yyyyMMdd}
```

数据库唯一索引：

```text
uk_biz_idempotent(biz_type, biz_id)
```

### 5.5.5 连续签到统计

连续签到可从当天开始向前扫描 Bitmap：

1. 获取当月 Bitmap。
2. 从今天 offset 向前遍历。
3. 如果遇到 1，连续天数 +1。
4. 如果遇到 0，停止。
5. 跨月时读取上月 Bitmap 继续统计。

为了降低频繁计算，连续签到结果可短期缓存：

```text
user:checkin:streak:{userId}
TTL: 当天 23:59:59 过期
```

### 5.5.6 MySQL 持久化

Redis Bitmap 用于高并发实时判断，MySQL 用于审计和长期查询。

表：

- `user_checkin_record`

写入策略：

- 签到成功后同步写 MySQL，保证流水可追溯。
- 或者先写 Redis，再发 MQ 异步落库。第一阶段建议同步写，逻辑更简单。

## 5.6 积分模块

### 5.6.1 积分来源

积分来源包括：

| 行为 | 积分 | 幂等规则 |
| --- | ---: | --- |
| 每日签到 | +5 | 每用户每天一次 |
| 连续签到 7 天 | +20 | 每周期一次 |
| 完成视频学习 | +10 | 每用户每视频一次 |
| 发布帖子 | +5 | 每帖子一次 |
| 发表评论 | +2 | 每评论一次 |
| 内容被点赞 | +1 | 每点赞事件一次 |

### 5.6.2 积分账户模型

用户积分分两类：

- 当前可用积分：`available_points`
- 历史总积分：`total_points`

扣减积分时减少可用积分，不减少历史总积分。

增加积分时：

- `available_points += points`
- `total_points += points`

### 5.6.3 CAS 乐观锁

积分账户表包含 `version` 字段。

更新 SQL：

```sql
UPDATE user_account
SET available_points = available_points + ?,
    total_points = total_points + ?,
    version = version + 1,
    updated_at = NOW()
WHERE user_id = ?
  AND version = ?;
```

如果影响行数为 0，说明并发冲突，进行有限重试。

重试策略：

- 最多重试 3 次。
- 每次重试重新读取最新账户。
- 仍失败则记录错误日志，并将事件投递到补偿队列。

### 5.6.4 积分幂等

积分发放必须先查幂等，不允许只依赖业务代码判断。

积分流水表唯一索引：

```text
uk_biz_type_biz_id_user(biz_type, biz_id, user_id)
```

例如：

```text
biz_type = VIDEO_FINISH
biz_id = videoId
user_id = userId
```

同一用户同一视频完成多次，只会生成一条积分流水。

### 5.6.5 积分事件消费

事件来源：

- 视频服务发送 `VIDEO_LEARNING_FINISHED`
- 论坛服务发送 `POST_CREATED`
- 论坛服务发送 `COMMENT_CREATED`
- 用户服务发送 `CHECKIN_SUCCESS`

消费流程：

```text
RabbitMQ 收到积分事件
  |
解析事件
  |
校验 eventId
  |
查询积分规则
  |
构造幂等 bizType + bizId + userId
  |
插入积分流水
  |
CAS 更新用户积分账户
  |
更新用户等级
  |
ACK 消息
```

### 5.6.6 MQ 消费可靠性

必须保证：

- 消息手动 ACK。
- 业务成功后 ACK。
- 业务失败 NACK 或进入死信队列。
- 消费者幂等，重复投递不重复加积分。
- 记录每次消费日志。

死信队列：

```text
xinglin.user.points.dlq
```

异常消息字段：

- eventId
- eventType
- userId
- bizId
- errorMessage
- retryCount
- failedAt

## 5.7 用户等级模块

### 5.7.1 等级规则

示例规则：

| 等级 | 名称 | 总积分区间 |
| --- | --- | --- |
| 1 | 初入杏林 | 0 - 99 |

### 5.7.2 等级更新

积分增加后，根据 `total_points` 重新计算等级。如果等级变化：

1. 更新 `user.level`。
2. 写入等级变化日志。
3. 发送用户成长通知事件。

等级规则可以先写在代码枚举中，后续迁移为数据库配置。

## 6. 数据库设计

## 6.1 user 用户主表

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
  username VARCHAR(64) NOT NULL COMMENT '用户名',
  phone VARCHAR(32) DEFAULT NULL COMMENT '手机号',
  password_hash VARCHAR(128) NOT NULL COMMENT '密码哈希',
  nickname VARCHAR(64) NOT NULL COMMENT '昵称',
  avatar VARCHAR(512) DEFAULT NULL COMMENT '头像',
  level INT NOT NULL DEFAULT 1 COMMENT '用户等级',
  status VARCHAR(32) NOT NULL DEFAULT 'NORMAL' COMMENT 'NORMAL正常 DISABLED禁用 LOCKED锁定 DELETED注销',
  token_version INT NOT NULL DEFAULT 1 COMMENT 'Token版本',
  last_login_time DATETIME DEFAULT NULL COMMENT '最后登录时间',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_username (username),
  UNIQUE KEY uk_phone (phone),
  KEY idx_status (status),
  KEY idx_created_at (created_at)
) COMMENT='用户主表';
```

### 6.2 user_profile 用户资料表

```sql
CREATE TABLE user_profile (
```

### 6.3 user_account 积分账户表

### 6.6 user_login_log 登录日志表

```sql
CREATE TABLE user_login_log (
```

## 9. 高并发设计

## 9.1 登录高并发

登录接口是高风险接口，不追求无限高 QPS，而是追求稳定和防攻击。

措施：

- IP 限流。
- 账号限流。
- 失败次数 Redis 计数。
- BCrypt 校验成本可控，避免 cost 设置过高导致 CPU 被打满。
- 登录日志异步写入或批量写入，避免主链路被日志拖慢。
- 对异常账号进行动态验证码。

## 9.2 签到高并发

签到可能在每天零点或活动期间集中爆发。

措施：

- Redis Bitmap 原子 SETBIT。
- MySQL 签到表唯一索引兜底。
- 积分发放通过 MQ 异步处理。
- 积分流水幂等防重复。
- 查询签到日历优先读 Redis。

## 9.3 积分高并发

积分会被视频学习、论坛互动、签到等多个模块同时触发。

措施：

- 积分发放走 MQ 解耦。
- 消费者按用户维度可做分区，降低同一用户并发冲突。
- CAS 乐观锁更新账户。
- 幂等流水唯一索引。
- 冲突重试。
- 死信队列补偿。

## 9.4 用户资料高并发

用户资料读多写少。

措施：

- 用户资料缓存 Redis。
- 修改资料后删除缓存。
- 热点用户资料可增加 Caffeine 本地缓存。
- 批量查询用户资料接口支持批量读取，避免 N+1。

## 10. 高可用设计

## 10.1 服务无状态

用户服务不使用本地 Session，不将登录态存 JVM 内存。所有实例都可以独立处理请求。

## 10.2 健康检查

服务提供：

```http
GET /actuator/health
```

健康检查内容：

- 应用存活
- MySQL 连接
- Redis 连接
- RabbitMQ 连接

## 10.3 优雅停机

配置：

- Spring Boot graceful shutdown。
- RabbitMQ 消费者停止接收新消息。
- 等待当前请求处理完成。
- 超时后强制退出。

## 10.4 降级策略

| 依赖异常 | 降级策略 |
| --- | --- |
| Redis 异常 | 登录失败次数和限流能力降级，核心登录仍可查 MySQL，但签到暂停 |
| RabbitMQ 异常 | 积分事件写入本地 outbox 表，后续补偿发送 |
| MySQL 异常 | 用户注册、登录、资料修改不可用，已签发 Token 短时间内仍可通过 JWT 校验 |
| 短信服务异常 | 短信验证码注册/登录暂停，密码登录可用 |

## 10.5 Outbox 补偿

对于重要事件，例如积分发放、等级变化、通知事件，建议使用 outbox 表：

1. 主业务事务内写业务表。
2. 同事务写 outbox_event。
3. 后台任务扫描 outbox_event。
4. 发送 MQ 成功后标记 SENT。

这样可以避免“数据库成功但 MQ 发送失败”的不一致。

## 11. 安全设计

## 11.1 密码安全

- 密码只存 BCrypt 哈希。
- 不记录明文密码日志。
- 修改密码后 tokenVersion + 1。
- 后台不能查看用户密码。

## 11.2 Token 安全

- JWT 使用强密钥。
- 密钥通过环境变量注入，不写入代码仓库。
- Refresh Token 存 Redis 哈希。
- Access Token 短有效期。
- Refresh Token 支持撤销。

## 11.3 接口安全

- 所有写接口要求登录。
- 管理接口要求 ADMIN 角色。
- 所有入参 Bean Validation 校验。
- 所有字符串字段长度限制。
- 禁止前端传入 userId 决定操作对象，必须从 Token 获取。
- 防止越权访问用户资料和积分流水。

## 11.4 XSS 防护

用户可输入字段包括昵称、简介、学习方向等。

措施：

- 后端过滤 HTML 标签。
- 前端渲染时不使用 `v-html` 展示用户输入。
- 富文本场景使用白名单过滤。

## 11.5 SQL 注入防护

- 使用 JPA 参数绑定或 MyBatis `#{}`。
- 禁止拼接 SQL 条件。
- 排序字段使用白名单映射。

## 11.6 CSRF 与 CORS

如果 Token 存 localStorage：

- 重点防 XSS。
- CORS 严格限制来源。

如果 Token 存 Cookie：

- Cookie 设置 `HttpOnly`、`Secure`、`SameSite=Lax/Strict`。
- 写接口启用 CSRF Token。

第一阶段建议前端使用 Authorization Header，减少 Cookie CSRF 风险。

## 11.7 敏感信息脱敏

日志和接口响应中：

- 手机号：`138****0000`
- 邮箱：`a***@example.com`
- Token：只打印前 8 位和后 4 位，或完全不打印。
- 密码：永不打印。

## 11.8 防刷和风控

需要限制：

- 登录接口
- 注册接口
- 短信验证码
- 签到接口
- 修改密码接口
- 修改手机号接口

限流维度：

- IP
- userId
- phone
- deviceId
- 接口路径

## 14. 缓存一致性设计

### 14.1 用户资料缓存

读：

```text
Redis -> MySQL -> 回写 Redis
```

写：

```text
更新 MySQL -> 删除 Redis
```

不建议写完立即更新缓存，因为并发写时容易产生脏数据。

### 14.2 积分账户缓存

积分账户更新频繁且一致性要求较高，第一阶段建议：

- 积分账户详情直接读 MySQL。
- 用户首页展示的积分可短 TTL 缓存。
- 积分变更后删除缓存。

### 14.3 签到缓存

签到状态以 Redis Bitmap 为实时状态，MySQL 为审计状态。

如果 Redis 丢失：

- 可通过 MySQL 当月签到记录重建 Bitmap。

2. 注册、登录、刷新 Token、登出。
3. JWT 鉴权过滤器。
4. 获取当前用户和修改资料。
5. Redis Bitmap 签到。
6. 积分账户和积分流水。
7. RabbitMQ 消费视频学习完成事件。
8. 日志拦截器、traceId、审计日志。
9. Docker Compose 接入 user-service。
10. 前端接入真实用户服务，替换当前 `X-User-Id` 演示登录。

第二阶段增强：

1. 手机验证码。
2. RBAC 权限表。
3. 管理员用户管理页面。
4. Outbox 事件补偿。
5. Prometheus 指标。
6. Sentinel 动态限流规则。
7. 用户风险画像。

## 21. 对现有视频服务的整改建议

视频服务需要同步补齐：

1. 增加请求日志 Filter，记录 traceId、userId、path、cost、responseCode。
2. 增加业务日志：详情查询、搜索、进度上报、点赞收藏、播放统计。
3. 增加 MQ 日志：学习完成事件发送成功/失败。
4. 增加异常日志：Redis、MySQL、RabbitMQ 异常必须打印堆栈。
5. API 响应增加 traceId。
6. 前端请求自动生成或透传 `X-Trace-Id`。
7. 替换当前前端固定 `X-User-Id`，改为用户服务 JWT 登录。

## 22. 总结

用户服务是杏林学堂的身份与成长中心。设计上必须同时满足功能完整性、安全性、高并发和可观测性要求。

核心设计原则：

- 登录态无状态，便于横向扩展。
- 密码只存哈希，Token 可刷新可撤销。
- 签到使用 Redis Bitmap 扛高并发。
- 积分使用幂等流水 + CAS 乐观锁解决重复发放和并发冲突。
- 所有关键行为必须记录业务日志和审计日志。
- 错误响应带 traceId，线上问题可以快速从用户反馈定位到日志。
- 依赖异常要有降级、重试或补偿机制。

按照该方案实现后，用户服务可以支撑视频学习中心、AI 助手、论坛和聊天模块的统一登录、用户资料、积分成长和安全审计能力。
